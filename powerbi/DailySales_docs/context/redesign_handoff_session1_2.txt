Design system for the pages
Every page should read top-left to bottom-right: filters, then KPIs, then trends, then
breakdowns. Every visual answers one stated question. The rules below combine the
design instructions, the brand booklet and the two inspiration articles. The articles stress
single-screen executive views, KPI cards with comparisons, tidy filter placement, and
hover detail instead of extra visuals.

Principles applied, or to apply:

 1. One question per page and per visual. Titles are written as questions ("Is paid revenue
    growing?") so they stay true when filters change.
 2. High signal-to-noise:
           no axis titles where the legend or title says it;
           dotted light gridlines;
           data labels instead of a value axis on bar charts;
           no shadows or 3-D;
           no legend title;
           at most 6–8 visuals per page.
 3. Colour carries meaning:
           cyan for the main series;
           greys for context;
           green, amber and red only for paid, pending and cancelled.
 4. Consistent grid:
           8 px spacing steps;
           same card radius (8) and border (#E3E5E8);
           KPI row in the same place on every page.
 5. Filters out of the way: a left rail holding all 17 fields, so the content area keeps the full
     width.
 6. Detail on demand: tooltip pages instead of extra charts.
 7. Correct numbers first:
           one measure family per page (revenue_orders_tbl);
           "incl. VAT" in the titles;
           never stack order counts by product.

an orders_invoices_tbl measure.

Automation notes
All edits were made in the Power BI service editor in Chrome, using in-page JavaScript
helpers. These notes are for whoever continues the build, by hand or with Claude.

      Helpers are patched off right now: to stop the layout run, window.pbiPos and
      window.selSpec in the open tab were replaced with no-ops. Restore them with
      window.pbiPos = window.__pbiPosOrig; window.selSpec = window.selSpecOrig . A
      page reload clears all helpers.
      Adding fields: wells accept a simulated HTML5 drag ( DragEvent with a
      DataTransfer ) from the Data pane tree item onto the well's "Add data fields here"
      box. Clicking a well does not open a field picker.
      Size and position: set the input values, then dispatch input, change and Enter events.
      The x / y limits are checked against the size the visual had when it was selected. So
      shrink first, deselect, reselect, then move. Width is capped at 1500 − x, so move a visual
      left before widening it.
      Title font-size trap: if the Title section is expanded above Properties, the first "size"
      input is the title font size. One title was briefly set to 60 pt this way.
